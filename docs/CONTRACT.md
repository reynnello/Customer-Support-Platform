# Общая база для двух участников и их AI

Главный источник имён, типов и сигнатур — `src/app.h`.

## Общие данные

- `Ticket`: `id`, `customer`, `subject`, `description`, `assignee`, `status`, `priority`.
- `AppState`: массив `tickets`, число записей `count`, следующий ID `next_id`,
  выбранный ID `selected_id`, признак несохранённых изменений `dirty`, строка `error`.
- Максимум 100 заявок. Используется диапазон массива `[0, count)`.
- Ёмкости строк включают завершающий ноль. Это байты, а не число символов Unicode.
- ID начинаются с 1; 0 означает отсутствие выбора. ID не равен индексу массива.
- Пустой assignee означает, что ответственный пока не назначен.
- Перечисления статусов и приоритетов, правила ошибок и поведения функций
  зафиксированы рядом с объявлениями в `app.h`.

Все пути выше относительно `src/`. Функции работы с заявками и файлами пока
только объявлены: реализаций нет, и UI их не вызывает. Реализованы только
инициализация состояния, названия статусов/приоритетов и пустое окно.
`ui_update` пока ничего не делает. Не путать основу с готовым функционалом.

## Как соединять части

Антон хранит поля ввода и UI-состояние в своём модуле. UI вызывает функции из
`app.h`, показывает `app.error`, выбирает заявку по ID. Поиск возвращает ID,
не копии записей и не индексы. Dzheffrei не добавляет Raylib в модули данных.

Перед изменением общего заголовка договоритесь друг с другом. Формат файла
Dzheffrei описывает отдельно до реализации. Путь по умолчанию — `tickets.txt`
в текущей рабочей папке; при первом запуске отсутствие файла обрабатывается в
`main`, а `storage_load` сообщает об этом как об ошибке. Реальные данные клиентов
не используйте и в Git не отправляйте.

Сначала объединяйте реализацию функций данных, затем UI, который их вызывает.
Проверяйте сборку каждого PR и общий сценарий после объединения. Мержить один и
тот же прототип повторно не нужно: обе личные ветки могут получить эту основу
обычным `git merge origin/main`.
